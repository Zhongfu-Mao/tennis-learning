# 网球 Wiki 定位与信息架构

定位确认日期：2026-10-13。

## 产品定位

面向普通球友的中文网球知识网站，支持按主题阅读、搜索、词条互链和来源查证。核心对象是可独立访问和分享的知识词条，而不是训练会话或个人档案。

首页呈现八个栏目、搜索入口和编辑精选。每个栏目有概念简介、子主题、词条列表、相关栏目。学习方法作为知识栏目，提供理解和观察方法；不要求打卡或开通账号。

不建设 VR 练习、个人 2.7→3.5/4.0 路线、训练日志、复习队列、订场联动或 AI 教练配置。旧相关内容仅在原始素材与 reference 代码中保留。

## 栏目与范围

| 主栏目 | 子主题与现有内容 | 后续补缺方向 |
|---|---|---|
| 入门与规则 | 球场区域、线、网高；分局盘；发球顺序、换边、报分、热身 | 不同赛制例外、双打顺序、规则版本和判罚说明 |
| 击球技术 | 准备、击球点、平衡随挥、发球抛球、一二发、接发 | 握拍体系、正反手分别展开、截击、扣杀、不同旋转发球 |
| 步伐与站位 | split step、距离、调整步、回位、宽球、开放/关闭站位 | 交叉步/并步、前后移动、网前移动与双打站位 |
| 球性与环境 | 上旋、切削、过网高度、弹跳窗口；风、阳光、温湿度、海拔、场地 | 更准确的球性条件、侧旋和轨迹示例 |
| 战术与比赛 | 深中路/斜线/直线；中性/防守/进攻；上网、穿越、挑高、对手类型；关键分 | 双打协作、阵型、沟通和模式拆解 |
| 体能、恢复与安全 | 专项力量、髋踝、减速；睡眠、补给、负荷；伤痛警示 | 专业来源、适用边界、避免诊断式和单因果表达 |
| 训练与学习方法 | 训练目标、热身、强度与休息、笔记、视频、复盘 | 将个人经验改写为带条件的方法；自测与概念解释 |
| 装备百科 | 球、球拍、球线、握把、球鞋、配件、维护 | 更明确的参数单位、适用条件和来源；不做无条件购买推荐 |

补缺方向是编辑待办，不代表当前已经覆盖。八栏目互有交叉：一张卡只有一个主栏目，可保留多个主题和相关词条链接，避免复制正文。

## 页面模型

规划路由（由 dots 实现，当前还没有可访问网页）：

- `/`：栏目总览、搜索、编辑精选。
- `/topics/<module-id>/`：栏目导航与子主题索引。
- `/wiki/<slug>/`：完整词条。
- `/search/`：标题、同义词、标签和正文检索。
- `/glossary/`：中文与常用英文术语、缩写和单位。
- `/about/sources/`：编辑方法、来源使用和修订规则。

词条顺序：概念摘要 → 内容解释 → 已通过审核的图解 → 常见误区/条件 → 相关词条 → 来源及修订日期。自测可作为简短阅读辅助，不构建复习系统。候选或需替换图片不充当已核实图解。

现有 `encyclopedia` 原文、摘要、相关卡和来源完整投影到 Markdown 草稿。个人等级、onCourtCue、verificationTest、VR/实场 drill 不投影。`commonFailure` 和 `reviewPrompt` 保留为待编辑素材，不能原样当成针对所有球友的建议。

## 内容状态

原始事实源：`content/atlas/cards/*.json`，并关联 `evidence-ledger.json`、`image-manifest.json` 和 `relationships.json`。

面向网站的 `content/wiki/catalog.json` 为每张卡登记唯一主栏目、稳定 slug、原始文件、原文哈希、图片状态、来源、编辑状态和待办原因。生成的 Markdown 是编辑交接件，不是最终发表稿。

所有卡本轮均为 `needs-wiki-review`、`publishByDefault: false`。`verified` 原状态保持不变，以免抹掉历史，但不能替代来源的逐项核对。日期沿用原版 `reviewedAt`，不把迁移日期伪装成事实核查日期。

规则、伤病、补给、环境、装备购买相关词条优先复核。需注明变体/赛制、观察范围、训练建议的适用条件。原版个人化判断如“你常…/根因多是…”、绝对措辞和未经支撑的固定百分比，要逐条改写。

## 实现建议

适合先采用内容驱动的静态网站：每个词条有独立 HTML、可分享链接和搜索索引，再加入需要的轻量交互。框架由 dots 在读完内容之后选择；不需要为了继承旧 UI 而继续 PWA App 架构。

初版优先阅读体验：桌面与手机目录、清晰正文、术语索引、图文关联、来源和搜索。收藏等功能以后再决定。无需后端账户系统。

旧 App 的 service worker 会尝试缓存整套图片，路径也按站点根目录编写，不能照搬到 Wiki 或 GitHub Pages 的项目子路径。实现时需处理部署 base、图像优化、缺图状态、页面 metadata 与链接检查。

当前工程仅准备 GitHub 内容交接。网站的框架选择、页面制作和正式部署交给 dots。
